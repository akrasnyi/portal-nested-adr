# Requirements progress

Tracks [requirements.md](requirements.md) against the code. Every requirement is tagged in the code with a comment
(`// FR-01: ...`, `{/* FR-04: ... */}`), so `grep -rn "FR-05" apps packages config scripts` jumps to it. `TODO` in a tag marks a gap.

Name mapping: App Hub = `apps/app-host` (`appHost`, route `/app-host`), CAD = `apps/use-case-a` (`useCaseA`, route `use-case-a`),
LayoutProvider = `BreadcrumbsProvider`, diagnostics = Use case A ProofPanel.

Both levels use static build-time remotes: the shell declares `appHost` in
[shell/vite.config.ts](../apps/shell/vite.config.ts) and imports `appHost/App`; App Host declares `useCaseA` in
[app-host/vite.config.ts](../apps/app-host/vite.config.ts) and imports `useCaseA/App`. No app calls the runtime API
(`registerRemotes` / `loadRemote`) itself; the code generated by `@module-federation/vite` does. All three apps set
`shareStrategy: "loaded-first"`: with the default `version-first` the shell fetched every entry in the chain at startup and
Use case A, not the shell, ended up as the React provider. With `loaded-first` the shell is the provider and each
`remoteEntry.js` is fetched only when its route is opened (checked in dev and build); the strictVersion error still fires.
A blocked remote is still contained ("currently unavailable"), but **Retry** in the same page no longer recovers: the
`?retry=n` re-registration from [results-failures.md](results-failures.md) (section 2b) belonged to the removed runtime
loaders. Evidence in [results.md](results.md) and [results-failures.md](results-failures.md) was recorded with runtime loaders.

Status: ✅ Passed · 🟡 In progress. Initial status comes from code review plus the evidence in [results.md](results.md)
and [results-failures.md](results-failures.md); re-check before you mark a row final.
